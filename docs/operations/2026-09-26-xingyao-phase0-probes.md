## 三、探针 2（Step 2）：零量行与 normalize_daily —— 不阻塞

Step 1 的结论是 xingyao **不产零量停牌行**（缺行），计划中"零量行被拒即停"的停止条件未被触发。

## 六、探针 5（Step 5）：配额口径 —— 1 计数单位 = 1GB 线上流量

**计数器位置**：登录时 tgw 打印的 logon json 含 `TotalWeekFlow` 与 `UsedWeekFlow`（`tgw.GetUsedWeekFlow`
函数不存在）。实测只解析这两个字段，其余（含 Token）一律不落盘。

| 读数 | 时刻 (UTC+8) | UsedWeekFlow |
| --- | --- | --- |
| 开盘（= 09-25 评估收尾值，同一周） | 09-27 00:08 | **0.23** |
| 探针 B 前 | 09-27 00:11 | 0.24 |
| 探针 B 后（2 个数据会话，~12k 行） | 09-27 00:11:54 | 0.25 |
| 收盘（全部数据探针后） | 09-27 00:38:22 | **0.45** |

**会话固定开销的专项实测（复核轮新增，2026-09-27 01:01:29–01:01:58，一个 60 s 可终止 worker 内完成，
无任何数据查询；授权依据：owner 2026-09-26 对 Phase 0 的授权，本探针为复核轮最小补充——
仅 5 个 login+日历会话，零数据查询、零存储载荷）**：读数 r1 → 1 个"login + 完整交易日历"会话 → 读数 r2（r2−r1 = 单会话开销）→
再 4 个同型会话 → 读数 r3（r3−r2 = 4 会话开销）。原始计数（非凭据字段）：
`r1=0.45, r2=0.45, r3=0.45`（`TotalWeekFlow=1,000,000,000` 不变）。

- `TotalWeekFlow = 1,000,000,000`。**口径钉死：计数单位是"周线上流量"，1 计数单位 = 1GB 线上传输量**
  （不是存储字节数；F 探针证明也不是按调用次数计费——5 个登录+日历会话计数器纹丝不动）。
- **计数器显示粒度 = 0.01 单位（=10MB）**；两次相邻读数 Δ=0.00 给出硬界。
- **【实测界】单会话固定开销（login + 完整交易日历，无数据）< 0.0025 单位**（单会话对 Δ=0.00，
  4 会话对 Δ=0.00 → 4F < 0.01）。此为上界；F 的真值可能远小（含为零）。
- **基数**：0.23 单位（09-25 评估后未翻周）；**本次消耗**：0.22 单位 ≈ 220MB 线上流量，覆盖
  ~45 个会话、516,657 行日 K（C/C2 精确：近窗 443,870 + 历史窗 72,787）+ 探针 A/B/D/D2 小窗
  ~320 行、11,862 行停牌状态、2 次全量代码表；**折算占比：本轮全部探针 ≈ 周配额的 22%**。
- **【推断】行级线上成本 ≈ 170–390 B/行（日 K）**：由本轮总账反推——0.22 单位 − 会话开销
  45×[0, 0.0025) = [0, 0.1125] − 代码表 ≈0.02（09-25 评估的计数器读数）→ 行账 [0.0875, 0.20] 单位
  ÷ 516,657 行。无法再收窄（须"读数对夹单一批次"的专项探针；标记为遗留不确定项）。
  09-25 评估的代码表标定（122,790 行 ≈ 10MB ≈ 81 B/行）低于该区间下端，说明不同端点的线上
  行形不同，行成本不能跨端点套用。
- **每轮增量窗口折算（数据本体，推断）**：校验车道一轮 = 已发布侧近窗实测 **46,785 行**
  （661 标的在 2026-06-15..09-22 已发布日线的实测行数，停牌标的的已发布零量行不在比对集内）
  × 170–390 B/行 = 8.0–18.2MB ≈ **0.008–0.018 单位 ≈ 周配额 0.8–1.8%**。全市场单轮回补按
  近窗实测外推（69 交易日实测 443,870 行，等长窗口 ≈ 44 万行）≈ 76–173MB + 少量会话 ≈
  **0.08–0.19 单位 ≈ 周配额 8–19%**。

### 23% vs 0.04% 的和解

两个数字**量的是不同的东西**，都真实：

1. **0.23（23%）是计数器读数**：累计**线上流量**（GB 口径）。评估报告当日全部探针 ≈ 0.23 单位。
2. **0.04% 是当时的载荷字节估算**：只数了"返回数据若存盘的压缩字节"（~400KB / 1GB），漏掉了
   (a) SDK 逐行 JSON 的线上膨胀（推断 ≈170–390 B/行，见上）、(b) 每会话固定开销（**实测界
   F < 0.0025 单位/会话**，评估套件 100+ 次调用即最多 ~0.25 单位量级）、(c) 代码表等大对象。
3. **分解模型（系数逐一标注来源）**：消耗 ≈ 会话数 × F + 行数 × B，其中
   **F = 会话固定开销 < 0.0025 单位【实测界，F 探针】**，
   **B = 日 K 行线上成本 ≈ 170–390 B/行【推断，由总账反推，区间无法再收窄】**。
   两个系数都不能当作点值使用：F 的真值在 [0, 0.0025) 内不可分辨，B 依赖端点行形
   （代码表 81 B/行 ≠ 日 K）。若 Task 11 需要点值，跑一次"读数对夹单一批次"的专项探针即可。
4. **运维口径结论**：做配额预算一律用计数器读数（`UsedWeekFlow`）；"存储字节估算"只可用于
   存储规划，不可用于流量配额。

### ⚠️ 接线成本发现（回 spec / ADR-016，Task 11）

校验车道 `_fetch_validation_daily` 按 `XingyaoSource` 契约**逐标的分发**（每次 fetch = 一个新 worker =
一次 login + 一次完整交易日历）。用钉死的系数重算一轮全宇宙（661 标的）校验的成本区间：

- 会话开销：661 × F，**F < 0.0025 单位【实测界】** → **[0, 1.65) 单位**——真值在"免费"与
  "周配额的 1.65 倍"之间，现有读数无法分辨；
- 数据本体：46,785 行 × 170–390 B/行【推断】→ 0.008–0.018 单位（≈0.8–1.8%）；
- **每轮合计：≈0.8%–167% 周配额**——最坏情形不可行，最好情形与批量通道同量级。
  **决定性未知数恰是 F**；要出点值，追加一次"读数对夹 ~20 个会话"或"读数对夹单一批次"的
  专项探针即可（本轮按复核约束只跑了 5 会话的界定探针）。

**定性结论成立且与 F 无关**：逐标的接线把同一次会话固定开销花 661 遍，批量通道只花 1–2 遍
（SDK `query_kline` 原生接受代码列表，本轮探针即以 1000 只/批抓取）；即使 F 落在零附近，
661 次登录握手本身也是每轮数十分钟量级的纯等待（界定探针 5 会话实测 27.5s 含 worker 启动，
外推 661 会话 ≈ 45–60 分钟）。扶正星耀或全宇宙跑校验车道前，spec 仍须先
解决"逐标的 worker 契约 vs 批量通道"的矛盾（选项：批量专用探针通道、缩小每轮标的集、降低轮频）。
本轮六项探针结论不受此影响。
