## 三、探针 2（Step 2）：零量行与 normalize_daily —— 不阻塞

Step 1 的结论是 xingyao **不产零量停牌行**（缺行），计划中"零量行被拒即停"的停止条件未被触发。
作为补充，用**合成行**验证了 `normalize_daily(frame, "xingyao", ts)` 的行级规则（明确标注：非供应商证据）：

- 零量行 + 合法价格（前收冻结、volume=0、amount=0）：**通过**，进入 valid（volume=0 为合法整数）。
- 零量行 + NaN 价格：被拒，reason=`invalid_number`——拒绝的是不可解析价格，不是零量。

结论：即便供应商未来改为返回零量行，现行 `normalize_daily` 无需放宽；不修改 normalize.py。

## 六、探针 5（Step 5）：配额口径 —— 1 计数单位 = 1GB 线上流量

**计数器位置**：登录时 tgw 打印的 logon json 含 `TotalWeekFlow` 与 `UsedWeekFlow`（`tgw.GetUsedWeekFlow`
函数不存在）。实测只解析这两个字段，其余（含 Token）一律不落盘。

| 读数 | 时刻 (UTC+8) | UsedWeekFlow |
| --- | --- | --- |
| 开盘（= 09-25 评估收尾值，同一周） | 09-27 00:08 | **0.23** |
| 探针 B 前 | 09-27 00:11 | 0.24 |
| 探针 B 后（2 个数据会话，~12k 行） | 09-27 00:11:54 | 0.25 |
| 收盘（全部探针后） | 09-27 00:38:22 | **0.45** |

- `TotalWeekFlow = 1,000,000,000`。**口径钉死：计数单位是"周线上流量"，1 计数单位 = 1GB 线上传输量**
  （不是存储字节数，也不是调用次数）。
- **基数**：0.23 单位（09-25 评估后未翻周）；**本次消耗**：0.22 单位 ≈ 220MB 线上流量，覆盖
  ~45 个会话、~54 万行日 K（443,870 + 72,787 + 探针 A/D 小窗）、11,862 行停牌状态、2 次全量代码表；
  **折算占比：本轮全部探针 ≈ 周配额的 22%**。
- **每轮增量窗口折算**：校验车道一轮"已发布 661 标的 × 62 交易日 ≈ 4.7 万行"的数据本体 ≈ 19MB
  线上流量 ≈ **0.02 单位 ≈ 周配额 2%**；即使每周 7 轮也只有 ~14%。
  全市场（5,235 只 A 股 × 62 交易日 ≈ 44.5 万行）单轮回补 ≈ 0.20 单位 ≈ **20–22%**，每周至多 4 轮量级。

### 23% vs 0.04% 的和解

两个数字**量的是不同的东西**，都真实：

1. **0.23（23%）是计数器读数**：累计**线上流量**（GB 口径）。评估报告当日全部探针 ≈ 0.23 单位。
2. **0.04% 是当时的载荷字节估算**：只数了"返回数据若存盘的压缩字节"（~400KB / 1GB），漏掉了
   (a) SDK 逐行 JSON 的线上膨胀（实测 ~380–420 B/行，约为 parquet 存储 ~90 B/行的 4–5 倍）、
   (b) 每会话固定开销（每次 login + 8,733 行交易日历 ≈ 4MB 线上流量 ≈ 0.004 单位；评估套件
   100+ 次调用即 ~0.4 单位量级)、(c) 代码表等大对象。
3. 本轮实测给出完整的分解模型：**消耗 ≈ 会话数 × ~0.004 + 行数 × ~400B**。按此模型反推 09-25
   评估（~100+ 会话 + 全量代码表 + 数万行）与其 0.23 读数吻合，误差在会话开销估计范围内。
4. **运维口径结论**：做配额预算一律用计数器读数（`UsedWeekFlow`）；"存储字节估算"只可用于
   存储规划，不可用于流量配额。

### ⚠️ 接线成本发现（回 spec / ADR-016，Task 11）

校验车道 `_fetch_validation_daily` 按 `XingyaoSource` 契约**逐标的分发**（每次 fetch = 一个新 worker =
一次 login + 一次完整交易日历 ≈ 0.004 单位固定开销）。若对全部 661 标的跑一轮校验：
661 × 0.004 ≈ **2.6–3.3 单位 ≈ 周配额的 260–330%，配额不可行**。SDK 的 `query_kline` 本身支持批量
代码列表（本轮探针即以 1000 只/批抓取）。扶正星耀或全宇宙跑校验车道前，spec 必须先解决
"逐标的 worker 契约 vs 批量通道"的矛盾（选项：批量专用探针通道、缩小每轮标的集、降低轮频）。
本轮六项探针结论不受此影响。

## 七、探针 6（Step 6）：成交量/成交额单位 —— 实测 (1, 1)

方法：4 只标的（000001.SZ / 600519.SH / 601238.SH / 300750.SZ）在近窗两侧共有交易日
